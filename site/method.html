Infrathon/Method

How a run works

Every task uses the same five-part specification. The agent works in its own container; a trusted controller enforces the deadline and reviews each submission; a separate judge runs hidden tests and scores the candidate. Nothing the agent can see contains private test data or scoring code.

Task specification τ = (W, P, E, R, T)

WWorkspace: starting code or an interface to implement, and the files the agent may edit.
PPublic tests: visible cases and a local runner for correctness checks and profiling.
EPrivate protocol: hidden test assets, task checks, the scoring objective and the feedback the agent may see.
RResources: GPU allocation and software runtime, per task.
TBudget: 12 h for operators, 24 h for modules and systems, including tool runs and judge waits.

Scoring

Each task keeps its own engineering objective: compute throughput for kernels, bandwidth for KV transfer, fidelity or retained accuracy for KV policies, quality gained per training hour for RL and distillation systems, and throughput for serving. A candidate that fails a correctness, quality or memory check scores by the task's rule, often zero. Infrastructure failures are kept separate from candidate failures and are never scored.

Run score

Every submission is evaluated by the private judge while the run is in progress. Submissions that pass all of the task's checks get a score; a run's result is the best of those scores, and the time it was reached is recorded alongside it. Infrastructure failures and integrity rejections never count as scores.

The rank score

Scores come in TFLOPS, tokens per second, compression ratios and accuracy points per training hour, so they cannot be averaged. Configurations are ranked within each task instead.

Per task, then averaged
RankScorem = mean over tasks τ of  100 · (nτ − ρτ,m) / (nτ − 1)

ρτ,m is the rank of configuration m on task τ by its best valid score during the run (1 = best; exact ties share the average rank; a run with no valid score ranks last) and nτ is the number of configurations that ran the task. 100 means first on every task, 0 means last on every task. Only the ordering matters, so the score does not change if a task's metric is rescaled; it also ignores how large the gaps are, which is why the mean relative score (a run's best ÷ the top score on the task) is reported alongside it.

Coverage

All 25 tasks count equally. Every configuration that ran a task is ranked on it. A run that never produced a valid scored submission ranks last there; a configuration with no run in the cohort is left out of that task instead of being counted as zero. All six configurations are ranked on 25 tasks; Miles OPD includes Astra’s earlier run.

Uncertainty. The leaderboard's 95% intervals and P(#1) come from resampling the task set with replacement. The Analysis page shows the full distribution of positions and what happens when single tasks are dropped.

Flags

Runs that differ from the rest of the cohort. They are ranked as recorded and marked wherever they appear.

Configurations and data

Six deployed model configurations, each run once per task. The comparison is between deployed configurations, not model weights alone.

Reasoning effort uses the unified display label max for all configurations (Appendix A.1). Astra was evaluated later than most of the other runs, under different service conditions. Results come from the selected October 25, 2026 export: 150 runs across 25 tasks, including Astra’s earlier Miles OPD run. Visible output tokens and agent actions follow Figures 5–7 and Appendix A.2 of the paper. The full allocated budget is 10,560 GPU-hours, including Work, continuously allocated Judge environments, and serving backends.
